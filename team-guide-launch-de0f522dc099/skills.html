Under the hood · deep dive

You’ve shipped a ticket down the paved road. Here’s the machinery underneath.

The main guide walked one feature down the funnel. This page opens the machinery: every skill behind those stages, each with a “watch it work” demo; how ticket-to-ship chains them; and the engineering decisions that made the workspace safe to hand to the whole team. Technical, but it still reads for a curious PM.

The skill system

Every skill, by phase

You work through three phases; each has its skills. For each: what it does, when it fires (dispatched automatically, or you invoke it directly), what it produces — and a ▶︎ Watch it work demo of the real exchange.

Delivery

ticket-to-ship is the delivery skill. It covers all the sister skills below — dispatching each at the right stage — and every one of them can also be triggered manually when you need it on its own.

ticket-to-ship The router

The one entry point, with two paths the operator chooses. Standard (default): finds where a ClickUp ticket already is (status, branch, open PR), loads only that stage’s playbook, runs its gate, records the result on the ticket, and stops — one stage per session. Lean one-shot (--lean): for a change you judge simple, the whole arc — implement → gates → review → draft PR — in a single session.

FiresDirect — the one you invoke: /ticket-to-ship FRC-813. It dispatches all the others.
One-shot/ticket-to-ship FRC-901 --lean — a trusted human call that the change is simple; it flags money-code touches in its closing report but doesn’t pause. You own the risk and the ladder review.
ProducesStandard: a flipped status, a handoff comment, and a paste-ready “start fresh” prompt — it refuses to roll into the next stage. Lean: a review-gated draft PR in one sitting.
›/ticket-to-ship FRC-813
ticket + branch + PR read → stage: Implement
one playbook loaded · gates run · findings fixed
✓ status flipped · handoff posted — then it stops
›/ticket-to-ship FRC-901 --lean
one-shot: implement → gates → review → draft PR, one session
✓ shipped in one sitting — your judgement it was simple
fix-bug Bug shortcut

The one-line front door for a simple ClickUp bug — a thin wrapper over ticket-to-ship --lean that makes the four things you keep forgetting the defaults: lean one-shot (no flag to type), a branch off the product default (latest staging), Sonnet (escalate to Opus only for genuinely hard diagnosis), and the heavy local verification pushed into a subagent so the main session stays small.

FiresDirect — /fix-bug FRC-832, from inside the repo. You never type “one-shot”.
EscalatesIf the change isn’t actually simple — money/settlement code, multi-behaviour, or UI needing the design gate — it stops and routes you to the standard ticket-to-ship path.

ci-diagnose Safety net

Triages a red CircleCI pipeline: what broke, which commit, and whether to revert or fix-forward. It knows the key trap — CI runs no PR-triggered tests, so a red pipeline means something already merged — and reads rollback behaviour per repo.

FiresAuto if a pipeline goes red mid-ticket — or direct: “CI is red”.

Runs before a release PR is opened: what’s shipping, does it silently undo anything, which migrations and config changes ride along. Proof is git ancestry, never the ticket status.

tdd / diagnose Implement stage

The two implementers ticket-to-ship dispatches to write the change: tdd builds features test-first (red-green-refactor); diagnose runs the disciplined bug loop (reproduce → minimise → hypothesise → fix). A bug fix always lands with the regression test that would have caught it.

FiresAuto in Implement — or direct (“use tdd”, “diagnose this”).

Two more sisters live in their home categories: design-gate (Design) fires for any UI ticket, and clickup-tickets (Utility) runs the Definition-of-Ready gate at stage Ready.

Utility

How it chains

How the skills chain

“Run ticket-to-ship” looks like one step. Underneath it’s a loop: read the ticket’s reality, pick the stage, load one playbook, run the gate, hand off. Here’s the loop.

How the skills chain
~1.5 min · watch the router read a ticket, pick a stage, and drive
Arrives with your brain update
What this video shows
  • The router reading the ticket status, the git branch, and the open PR — then picking exactly one stage.
  • One playbook file loading (and why the context stays small).
  • A gate going green: the status flip and handoff comment landing on the ticket, live.
  • The refusal: asking it to roll into the next stage, and it insisting on a fresh session.
  • The start-fresh prompt pasted into a new session that picks up exactly where this one stopped.

  1. It reads the artifacts, not its memory

    On /ticket-to-ship FRC-813, the router reads the live ClickUp ticket status, the git branch you’re on, and any open PR. Artifacts win: if the status says to-do but a PR is already open, it trusts the PR, treats the ticket as further along, and fixes the status.

  2. It picks exactly one stage

    It maps what it found onto the ladder — Ready → Implement → Triage → Staging — and commits to a single stage. It does not try to do two.

  3. It loads ONE playbook

    It opens only that stage’s file (e.g. stages/02-implement.md), not all of them. Less in the context window means a sharper agent — every extra page it carries gets re-read on every turn.

  4. The stage invokes its sub-skills

    Implement dispatches tdd or diagnose to write the change, then design-gate for UI, then the local QA gate, then pr-review — each a delegated step. The router orchestrates the skills above; it never duplicates them.

  5. The gate must pass before the status advances

    On green: it flips the ClickUp status, posts a handoff comment, emits a paste-ready “start fresh” prompt — then stops. On red: the status does not move; it reports plainly what failed and the one decision that’s yours (fix now, send back, get owner sign-off).

  6. A fresh session per stage — and why

    It refuses to roll into the next stage in the same session. A clean context is a hard rule, not a suggestion: a session’s cost is turns × context, and a stale, cluttered context is how agents drift. You paste the start-fresh prompt into a new session for the next stage.

StageGate(s) that must passSkills the router dispatches
Ready Definition-of-Ready — scope + acceptance criteria confirmed clickup-tickets
Implement Design gate (UI) + local QA + pre-PR review tdd / diagnose, design-gate, pr-review
Triage Copilot + SonarCloud findings judged & resolved (ADR-0011) review-triage
Staging Human checklist + staging smoke walkthrough agent browser walkthrough, then human rungs

The gate is the join between stages. The ClickUp status only moves when a gate is green, so the ticket’s status is always an honest record of how far the work really got — not a hope. ci-diagnose and release-check sit outside this per-ticket loop: one is the safety net when a pipeline breaks, the other is the promotion gate Tony runs across many tickets at once. And the --lean one-shot path skips the per-stage routing entirely — the whole arc in one session — when the operator explicitly judges the change simple.

Under the hood

The decisions behind the workspace

Two things made the team rollout possible: GRC-2302 collapsed local setup to one config, and a handful of ADRs fixed how work flows. Here they are, for the engineers.

GRC-2302 — one config is the whole local truth

The old per-machine user-secrets maze is gone. The checked-in appsettings.Development.json is now the single source of truth for local boot:

  • Local databaselocalhost:5432 · local-ecf-db · user postgres, with the password checked into appsettings.Development.json — exactly what the Docker Postgres serves.
  • Hangfire jobs DBlocal-ecf-jobs, created on first boot by infra/pg-init/.
  • Docker imagepinned postgres:13 — staging parity, so “works locally” means something.
  • Only user-secret leftAzurite storage (UseDevelopmentStorage=true). Everything else is checked in.
  • DB clientnone required — seeding happens on boot. DBeaver (or any SQL client) is optional, for browsing only. Docker Desktop is the one hard runtime dependency.

One sharp edge remains: EF migrations. The design-time factory ignores user-secrets, so before any dotnet ef command you export the connection string by hand (single-quote it — the ! trips history expansion):

Before dotnet ef — Mac, Linux & Windows (bash) export ConnectionStrings__DefaultConnection='Host=localhost;Port=5432;Database=local-ecf-db;Username=postgres;Password=<see appsettings.Development.json>'

Each of these boot fixes used to live only on a temporary local-dev branch. They were upstreamed — one reviewed PR per codebase, environment-gated so they never affect a real deploy — and then that temporary branch was deleted. Getting the code running no longer needs a special branch.

The ADRs that shaped the rollout

One paragraph each. The full decisions live in pitchplatforms/ADRs — discover them with bin/adr-get --list, read one with bin/adr-get <n>.

ADR-0012 Upstream the boot carries

The ~40 lines of local-boot plumbing (DbSeed, dev-cert, local ports, the Playwright harness) that used to live on never-merged local-dev branches were upstreamed into each product default, environment-gated so staging/production behaviour is byte-identical — then local-dev was retired. Any branch cut from the default now boots and seeds out of the box, which is what makes the branch-off-default team model possible.

ADR-0013 ClickUp is the sole tracker

The dual-tracker model (ClickUp plus a parallel GitHub-issues layer that fed the retired Ralph loop) is gone. The ClickUp ticket is the unit of work, end to end — the only intake gate, linked to branches and PRs by the <REF> convention. Every bridge between two trackers was a silent-breakage point; now there is one system, no carve-outs.

ADR-0014 Read-only brain + paved-road router

The workspace is distributed read-only — the owner pushes, the team pulls, a session-start hook checks for updates and asks before applying. The 33-skill à-la-carte menu is replaced by one router (ticket-to-ship) as the sole documented entry point; it enforces the hard context rules (one stage per session, delegated reads, isolated worktrees) as code, not advice. The Ralph loop retires.

ADR-0017 + ADR-0025 The feature branch is the promotion unit; PRs enter in two tiers

Work rides feat/<REF>-<kebab> branched off the product default — still the unit that promotes staging → uat2 → master (ADR-0017). ADR-0025 amends how changes enter it: every change arrives via a topic-branch PR into the feature branch — never a direct commit, even solo — which the feature owner squash-merges into one clean <REF> <short lowercase description> commit. The whole feature then crosses into the default as one integrator-run PR — merge commit, never squash (the feature branch re-merges, and a squash desyncs it). A feature’s bug fixes ride the same branch, so they can never be promoted apart from it.

ADR-0022 ADRs move to their own repo

ADRs now live in their own team-writable repo (pitchplatforms/ADRs), not inside the read-only brain — GitHub can’t make one repo “read-only except one folder”, so the decisions that the team still publishes itself got their own home. Cite by number, read with bin/adr-get <n>, discover with bin/adr-get --list; the brain keeps no local ADR files.
