The two rules the whole shape follows1 · The checklist an issuer sees is a copy of a template, made when they apply — or when admin moves an application already in progress onto the portal (P2P-124). The library and the templates can change any time; a live checklist never notices.
2 · Everything that happens afterwards adds a row and never overwrites one — a re-upload keeps the old file, a return keeps its reasons, a waiver that ends gets a second line saying so.

How a whole offer fits in one row

The Detail column holds structured text. For an offer, that is the shared block plus the block for its asset class — which is what lets an equity or token block be added later without touching the table.

kind:    TermsProposed
who:     Sam Doe · issuer
detail:  { "shared": { "shariahType": "Conventional", "purpose": "WorkingCapital",
                     "minimumToRaise": 400000.00, "maximumToRaise": 500000.00,
                     "securityOffered": ["PersonalGuaranteeFromDirectors"] },
           "note":   { "financingType": "BusinessTerm", "tenure": 36 } }

kind:    TermsEdited
who:     Alex Doe · admin
detail:  { "field": "rate", "from": null, "to": 11.0 }

Nobody searches these rows for numbers. When admin creates the funding round, the approved terms are copied into ordinary columns on Campaign and CampaignNoteTerm, and everything downstream reads those.

This is the activity log, not the status. The status is the one word the issuer sees on their checklist (six of them — see how a status moves). A record is one thing someone did to the item. Some records change the status (accepted, returned, waived); others do not (a note to the issuer, an edit to the terms, sign-off).

One table, many kinds — so what each kind must contain is checked in codeA waiver needs a written reason; an acceptance does not. One table cannot make a column compulsory for some rows only, so the database allows blanks and the application checks before it saves. Two things keep that safe, both part of story 31.A: the list below, and one automated test that fails if any kind can be saved without what it must contain — the same discipline the status sentences follow.

New — set up once, then copied (5)

RequirementItemThe menu. Every document, form, fee or check pitchIN can ask an issuer for, written once by admin.

For example: "Bank statements, last 6 months" — a document upload, PDF only, up to 6 files.

What it holds
  • the kind of item — ItemType, a new enum (not RaiseFundApplicationActionType)
  • section (a closed list of five)
  • name · optional help text
  • file rules: formats, how many files, size each, must-include lines
  • settings for its kind: which form to show (DynamicFormTemplateId) · the fee (FeeAmount) · the statement to confirm (title, lines, body) · what admin checks
  • extraction flag (reserved for reading documents automatically, later)
RequirementTemplateA named shopping list for one type of application at one moment — what a note issuer is asked for when they submit, or once they are approved.

For example: "Note · at submission".

What it holds
  • name
  • application type (asset class)
  • its role for that type: at submission or at approval
  • whether it is the default for that type and role

Exactly one template is the default for each type and role, and those are what an application gets automatically. Other published templates can exist; admin swaps one in by hand (P2P-74), and changing an application's type swaps it onto the new type's templates the same way (P2P-124). Four ship seeded by name, with an empty library: Note and Equity, each at submission and at approval.

RequirementTemplateVersionA numbered print-run of the list, so we always know exactly which list an issuer was given.

For example: "Note · at submission · v1, published 18 Jul 2026".

What it holds
  • template · version number
  • state: draft or published — admin edits the draft; publishing freezes it, and the next edit starts a new draft
  • published when, by whom

A published version freezes which items, their order and whether each is required. It does not freeze their wording: that is copied from the library at the moment an issuer applies.

RequirementTemplateItemOne line on the list: which library item, in what position, required or optional.

For example: Line 9 of "Note · at submission · v1" is "Bank statements, last 6 months", required.

What it holds
  • template version · library item
  • position in the order
  • IsRequired (default true) — required belongs to the line on the list, not to the library item
ApplicationRequirementOne line on one issuer's checklist: a photocopy of the library item taken the day they applied, plus where it has got to.

For example: Terra's "Company constitution" — Returned.

What it holds
  • the application it belongs to
  • the copied content: name, help text, file rules, settings for its kind
  • kind · required or not · status (six live values; Past due is reserved)
  • which library item it was copied from — for matching only, never read for wording; empty for a one-off item admin added to this application only (P2P-74)
  • which template version it came from — empty for any item admin added later
  • whether it is waived · whether it has been removed from this application (P2P-74 — what was sent is kept)
  • a note from pitchIN — admin's words for this issuer about this item ("the guarantee from Encik Razak, stating the amount"), shown under the help text, editable until the item is accepted
  • fee items: the id of the existing payment row
  • offer terms items: the current offer, whether the issuer has confirmed it, whether it is locked, the approved terms, and the funding round created from them with its note reference (P2P-87)

Screens read status, waived, confirmed and locked straight from here. They are never worked out from the logbook.

New — what happens on a checklist item (3), and help (1)

FileVersionEvery file ever sent for an item, newest on top. A new upload sits beside the old one; nothing is replaced.

For example: Company constitution: version 1 (returned), version 2 (accepted).

What it holds
  • checklist item · the file, in the existing Attachment store
  • where it came from: issuer upload · camera · admin on their behalf
  • who · when

A proof of bank transfer on a fee item is a file version too, and so is an executed agreement (phase 2).

FormSubmissionEvery time a form was sent in. The answers themselves stay where the existing form module keeps them.

For example: Debtor ageing listing · round 1 · filled in by the issuer.

What it holds
  • checklist item · the existing UserDynamicFormSubmission row holding the answers
  • round number
  • FilledBy: Issuer or Admin
  • sent when

A saved draft leaves the item In progress; sending it makes the item With pitchIN.

RequirementRecordThe logbook. One line each time someone decides, confirms or writes something — returned, accepted, waived, a note to the issuer, signed off — with who, when and why.

For example: "5 Aug · Company constitution · Returned · Alex Doe · Pages 4 to 7 are missing — send the complete copy".

What it holds
  • the application — always
  • the checklist item — when the line is about one item (sign-off and a template swap are about the whole application)
  • kind of record (the list above)
  • who · their role (issuer, admin, system) · when
  • the reason, in admin's own words — shown to the issuer on a return, kept internal on a waiver
  • detail — what that kind needs, as structured text: the file version judged, the wording confirmed, the offer proposed, the field changed …

Append-only: lines are added, never edited or deleted. Today's Remark is one string overwritten on every review; this is what closes that gap.

HelpRequestA message from the issuer saying "I'm stuck", kept here and handed to support as a ClickUp task.

For example: "Can we do 30 months instead of 36?" — raised from the Offer terms item.

What it holds
  • application · the checklist item, if raised from one
  • message · who · when
  • ClickUp task id — empty if ClickUp could not be reached; the message is kept either way

Existing, gains columns (1)

CompanyFundApplicationThe issuer's application, exactly as today. It learns three new things: what they are raising with, whether it has the portal, and when onboarding was signed off.

For example: Terra · Note · onboarding complete, signed off by Alex Doe on 12 Sep 2026.

What it holds
  • AssetClass — Equity 1 · Note 2 · Token 3, the same enum Lane A puts on Campaign
  • has the portal (yes/no) · moved at · moved by — empty when the switch gave it the portal (P2P-124)
  • onboarding complete · signed off by · signed off at (P2P-73)

Asset class is set at submission: until the intake (P2P-30) sets it, it is stamped from the submitted form's DynamicFormTemplate.ProductType — P2P → Note, ECF → Equity, TCF → Token. Existing rows read Equity. Admin can change Note ↔ Equity with a reason until sign-off (P2P-124).

Who has the portal is this one marker, never the switch. An application gets it when created while the switch is on, or when admin presses Move to new portal; every screen reads the marker, so turning the switch off never takes the portal away. Without it, the application keeps today's screens untouched. Token applications never get it.

Built in Lane A, written to once (2)

CampaignThe funding round. Onboarding writes to it once, when admin presses Create funding round.

For example: N-2026-00042, created as a draft from Terra's approved terms.

What it holds
  • written from the approved terms: ShariahType · MinimumTargetAmount / MaximumTargetAmount · MinimumInvestmentAmount · asset class

The round is a copy, made once through Lane A's note service — never a live link back into the checklist. Reopening the terms while the round is still a draft overwrites the draft in place.

CampaignNoteTermThe note's terms as the listing will show them. Filled from the approved offer at the same moment.

For example: Business term · 36 months · 11.0% · grade B1.

What it holds
  • written from the approved terms: financing type · tenure · repayment · purpose · risk grade and rationale · rate · face value, advance rate and counterparty for invoice or purchase-order financing
  • stamped by Lane A's service: the fee and servicing terms · the note reference
  • SecurityOffered — personal guarantee · corporate guarantee · post-dated cheques · other
  • SecurityOther

The two security columns are the only thing this lane adds to Lane A's table (P2P-87). The guarantee documents themselves are checklist items admin adds by hand (P2P-74).

Existing, reused as it is (4)

CompanyFundRaiseApplicationProcessToday's checklist keeps one of these rows per step per application — that step's status, file, form or payment. The portal does not use it for steps at all. It uses it for one thing: a fee's payment row, because the FPX code writes here and is left untouched.

For example: Terra's onboarding fee — FPX, paid.

What it holds
  • one row per fee item, created on the first attempt, of type FPXPayment or UploadReceipt
  • PaymentGatewayReferenceNumber — the FPX reference · AttachmentId — the proof, if by transfer
  • its status drives the item: PendingFPXApproval or proof uploaded → With pitchIN · Paid → Accepted · BypassPayment → Accepted and waived
UserDynamicFormSubmissionWhere the existing form module keeps a filled-in form. The portal reuses the module whole, so a form item needs no new form builder.
What it holds
  • one row per round, pointed at by a FormSubmission
  • the answers, as the module stores them today (UserDynamicFormAnswer)

Fields are designed in form management, not in the library. There is no table field today; spreadsheet import (P2P-85) adds one first.

AttachmentThe platform's file store. Every file version points at one file here, stored as uploads are stored today.
What it holds
  • the file, as today

Phase-2 Google Drive import (P2P-84) copies the file here at once; a link to Drive is not a record.

ClickUp taskWhere the support team picks up a help request.
What it holds
  • one task per help request, in Customer Support › Fundraising Query (the list id is a new setting beside the existing ClickUp ones)

Support replies by email or phone. Replies inside the portal are P2P-78.

Legacy, kept untouched (1)

FundRaiseApplicationStepToday's fixed checklist. Left alone, so in-flight ECF applications keep working on the old screens.
What it holds
  • a step's type, title, order and admin-only flag — one fixed list per module, read live by the old screens

It has no template, version or copy-per-application, which is why the engine is new tables rather than an extension of this one. P2P-77 retires it once nothing runs on it. Nothing is migrated: in-flight applications are moved one at a time with Move to new portal (P2P-124), and their old rows stay where they are.
