How the onboarding portal works, step by step

When a company applies to raise money on pitchIN, we ask them for documents, forms and fees before we can approve them. Today that happens over email, Google Drive and WhatsApp. The portal puts it all on one checklist. This page follows one company — Terra Agritech Sdn Bhd, applying to raise with a note — through everything that can happen, and shows what gets saved at each step.

Companion to Lane C (epic P2P-63): P2P-31, 87, 73, 74, 77 Read with the clickable prototype

Who is involved

IssuerThe company raising money. They see a checklist of what we need from them, send things in, and see what has been accepted or returned.
AdminpitchIN staff, working in the admin portal. They set up what gets asked for, review what comes in, and accept, return or waive each item. "Reviewer", "analyst" and "ops" in the tickets and the prototype all mean admin; there is no difference in permission.
InvestorNot part of onboarding. Investors see nothing of it. A funding round exists only once admin creates it from the approved offer terms, and investors see it only when it is listed.

Five words this page uses

  • Requirement — one thing pitchIN can ask an issuer for, defined once in the library: a name, an optional line of help text, a kind, and the settings that kind needs. Admin writes these. In the tickets this is the library item, RequirementItem. The tickets' "requirements" (plural, on a file item) means something narrower: the typed limits block — formats, how many files, size, and the "must include" lines.
  • Template — an ordered list of requirements, published as numbered versions. Each application type (asset class: Note, Equity, Token) has two: the at-submission template, snapshotted when the issuer submits, and the at-approval template, merged in when the application is approved. Exactly one template holds each (type × role). They ship seeded by name — "Note · at submission", "Note · at approval", "Equity · at submission", "Equity · at approval" — with an empty library.
  • Checklist item — one requirement on one issuer's checklist. It is a copy of the requirement's content, taken from the library when the application is snapshotted. Library and template edits never reach it; only the automatic at-approval merge (P2P-31) and a deliberate, reason-logged admin change (P2P-74) can alter it. It has a kind, a status, whether it is required, and its own records (below). Everything the issuer and admin do happens on checklist items.
  • Kind — what sort of thing the item is. The kind decides what the issuer does and what admin sees. The tickets and every admin screen call this the item type, and use different names. Plain name here → type in the tickets: Document upload → File request · Form → Form · Fee payment → Payment · Acknowledgement → Acknowledgement · Checked by pitchIN → Admin-verified · Offer terms → Offer terms · Agreement signing → Signature (phase 2) · Task on another page → In-platform task (phase 2). Admin screens render the type name, never the plain name. The issuer never sees either — only the item's name.
  • Status — where the item is: Not started, In progress, With pitchIN, Returned, Accepted, Out of date. The sentence the issuer reads for each status is fixed per kind; admin never writes it. The checklist groups rows by whose court they are in — Issuer (Not started, In progress, Returned, Out of date), pitchIN (With pitchIN), Nobody (Accepted) — and never labels a group as a priority. A seventh status, Past due, is reserved in the model and never set or shown; no due date renders anywhere.

Words that are easy to mix up

  • Four different approvals. Application approval — Lane B (P2P-62) decides whether we work with this business; it triggers the at-approval merge. Terms approval — admin approves the offer terms item (P2P-87). Onboarding approval, also called sign-off — one admin closes the application when every required item is accepted or waived (P2P-73). Accepting one item — every review. None of them makes a funding round visible to investors.
  • Acknowledgement is both a kind of item and the name of a child record. The kind is the item the issuer reads and ticks; the Acknowledgement record is the row one confirmation writes. This page calls the record an acknowledgement record.
  • Funding round (what the issuer reads) = Campaign (code) = listing (what investors see). The note is the instrument, created at close (P2P-26).
  • Return / Returned is the one word for admin needing something different. Attest / Withdraw is the pair for an admin-verified item. Waive records that an item is not needed; it is also the only way to undo an acceptance.

How it fits together

Three ideas, in order. Admin defines requirements once. Admin picks which ones go on a template. Each application gets its own copy of the template. Library and template edits never reach it; only the automatic at-approval merge and a reason-logged admin change (P2P-74) can alter it.

What a published version freezes, and what it does not. A published template version freezes membership, order and whether each item is required. It does not freeze content: when an application is snapshotted, each item's content (name, help text, file limits, per-kind settings) is copied from the live library item at that moment. So a library edit reaches the next application without republishing the template, and never reaches an application already running. The snapshot keeps the library item's id for matching only; it is never read back for content.

Where the deal comes from

At onboarding, all we know is what the company applied to raise with. Under the company name the checklist says "Note terms to be agreed". The deal is agreed on one checklist item, Offer terms, and the funding round is created from it afterwards.

How the deal is agreed

  1. The issuer proposes what only they know: financing type, purpose, how much (or the invoice or order behind it), for how long, Shariah type, and what security they can offer.
  2. Admin completes the offer — a copy of the proposal — adding what only pitchIN decides: risk grade and rationale, the rate within the grade's band, the minimum per investor (from config unless changed), and for invoice or purchase-order financing the advance rate. Repayment is derived from the financing type; admin can override it. Admin may also change anything proposed.
  3. The issuer confirms the offer — always, because it carries the rate and grade they have not seen. Every field that differs from their proposal is marked. Confirm is their only action; if they disagree they use Help and admin edits the offer. The offer is locked while they are confirming, and any edit after confirmation needs confirming again.
  4. Admin approves. The headline now shows the deal. This can happen at any point in onboarding.
  5. Admin creates the funding round — a separate, deliberate action. The approved terms are copied into the round once, and the note reference is issued. The terms then lock while the round exists.

Onboarding data stays in onboarding. The round is a copy made at step 5, not a link back into the checklist — the round's terms have to be the record the listing showed, frozen once set up. To change terms after that, reopen the item while the round is still a draft: it moves back to With pitchIN with the offer unlocked and the confirmation cleared, the issuer confirms again, admin approves again, and Create funding round overwrites the draft round's terms in place, keeping the note reference. Once the round has left draft, the item cannot be reopened. After onboarding sign-off, Create funding round and reopen are the only item actions still offered.

Building blocks in the prototype

The first section of every checklist in the prototype, Building blocks, holds one placeholder item per kind. Every text on it names where that text comes from — "[Item name — admin types this in the library]" — and its page carries a guide: what admin sets up, what the issuer's page shows, what the issuer can do, what admin sees when reviewing, and what gets saved. The placeholder, its bracketed texts, the "Building blocks" section, the guide box, the persona bar, the seed data, and every count and progress line ("2 of 20 done", "used by 3 templates") are build guidance only — none of them exist in the product, and no ticket specifies a count or a progress bar. Read the guide's five headings as the build notes for that kind; the component below the box is the reference for what the issuer actually sees. Controls marked phase 2 (Google Drive, spreadsheet import) are not rendered in phase 1.

Where it is built, and in what order

Four repos and one test-scripts repo. The portal is a new page beside the existing one: new tables for the engine, with the existing application, attachment and payment tables referenced by foreign key.

The routing rule at launch

An application's asset class is a column on the application (CompanyFundApplication.AssetClass: Equity, Note, Token), stamped at submission from the submitted form's ProductType until P2P-30 takes over. Only an application whose asset class is Note opens the new checklist and the new admin tab. Every other application stays on the existing screens, untouched, until P2P-77 moves everyone across. The equity templates are seeded so the wiring is testable; no equity application reaches the portal before P2P-77.
