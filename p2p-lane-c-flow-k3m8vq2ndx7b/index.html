What we are building

TodayAfter a company applies to raise, pitchIN collects its documents, forms and fees over email, Google Drive and WhatsApp. Nobody can see what is outstanding without asking.
What this buildsOne checklist per application. The issuer sees exactly what is left to do. pitchIN staff see exactly what is waiting on them, review each item, and sign the application off.
The twistThe checklist is not a fixed list of documents. Staff define what can be asked for and assemble lists from it, without an engineer. Nobody gets it until pitchIN switches it on (P2P-124): one application at a time with Move to new portal, then every new note and equity application. Token applications come later.

Six ideas to hold in your head

Everything in the tickets follows from these.

1

Menu → list → copy

Admin writes a library of things we can ask for. A template is an ordered pick from it, published as numbered versions. When an issuer applies, their checklist is a copy. Editing the library or a template later never touches a checklist that is already running.

2

Eight kinds of item, and no more

Admin can add any number of items, but each must be one of a closed set of kinds. A new kind is an engineering ticket. That is what stops this becoming a form builder.

3

One status per item

Not started · In progress · With pitchIN · Returned · Accepted · Out of date. Admin writes an item's name and help text; the sentence describing its state is fixed by the product, per kind, so it reads the same everywhere.

4

Nothing is overwritten

A re-upload sits beside the old file. A return keeps its reasons. Every decision — accepted, waived, signed off — is a new line in one logbook, with who and when. History is never reconstructed; it is simply there.

The tables →
5

Four approvals that are not the same

Accept one item. Approve the application — we will work with this business (Lane B). Approve the terms — the deal. Sign off — onboarding is complete. None of them lists anything to investors.

The words, side by side →
6

The deal lives on one item

The issuer proposes terms, admin adds the grade and rate, the issuer confirms, admin approves. Only then does a separate action copy the terms into a funding round. Onboarding data stays in onboarding.

The flow, end to end

One application, from applying to a funding round. Steps 3 and 5 repeat until everything is in.

  1. IssuerSubmits the application form

    That is Lane B's intake (P2P-30), not this portal. It tells us the asset class: Note, Equity or Token. Whether this application gets the portal is P2P-124: the switch (off by default), or admin pressing Move to new portal later. Note and equity can; token cannot. Without the portal, today's screens carry on unchanged.

  2. AutomaticTheir checklist is created

    Only for an application that has the portal. A copy of its type's at-submission template ("Note · at submission" or "Equity · at submission") — the light list, so they can start early.

  3. IssuerSends items Adminreviews each one

    Each item is sent on its own, whenever it is ready; only forms can be saved as a draft. Admin accepts it, returns it with a reason, or waives it. Any admin can act on any item.

  4. Lane BApproves the application Automaticthe fuller list merges in

    The "at approval" items are added. Nothing already on the checklist is removed or reset.

  5. IssuerAdminAgree the offer terms

    Note applications only. Propose → admin completes the offer → issuer confirms → admin approves. It can happen at any point, and sign-off waits for it. An equity application has no offer-terms item until P2P-88 and keeps today's Offer creation step.

  6. AdminSigns off onboarding

    Allowed once every required item is accepted or waived. The issuer reads "Onboarding complete. We have everything we need."

  7. AdminCreates the funding round

    A separate, deliberate action, before or after sign-off: the approved terms are copied once into the round through Lane A's note service (P2P-26) and the note reference is issued.

Rules that are easy to break

  • A checklist item never reads the library for its wording. It keeps the library item's id for matching only.
  • Help text describes the requirement, never its state. The same sentence shows whether the item is untouched, returned or accepted.
  • Accept and Return appear only when something was actually sent — judged from what was sent, never from the status.
  • Who has the portal is one marker on the application, never the switch. An application gets it when created with the switch on, or when admin moves it; turning the switch off never takes it away (P2P-124).
  • An equity application has no offer-terms item — not a disabled one, not a placeholder — until P2P-88 ships.
  • Any admin can act on any item. There is no new role, no team ownership and no assignment.
  • A waived item shows the issuer as Accepted. Admin's reason is never shown to them. Waiving is also the only way to undo an acceptance.
  • The prototype is a walkthrough, not the build. It does not do four things the tickets require: the automatic merge at approval, keeping every review round, recording attest and withdraw, and keeping a waiver as a record. Its counts, names and top bar are demo only.
