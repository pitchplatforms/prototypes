▲ serious 4 · Production-only code that staging never received (193 commits)

Production carries 193 commits whose content does not exist on staging (patch-equivalence checked, merges excluded). Two consequences: (a) everything verified on staging is verified against code that is not what production runs; (b) any branch-level promotion of staging into production risks reverting these commits — which has already happened once (see the gateway note below). Each commit needs to be either back-ported to staging or consciously recorded as prod-only.

  • Platform drift: the production branch received its own .NET 10 upgrade, the /modules folder restructure, dependabot dependency bumps (AutoMapper, AWSSDK.S3, Azure.Storage), and an /internal/version endpoint — none of which exist as the same patches on staging. Staging literally runs a different platform than production.
  • Payments config: “Update FPX private key path in appsettings.json” exists only on prod — a payment-gateway config staging doesn't mirror.
  • Security fixes: SEC-399 / SEC-396 (draft announcements visible to the wrong users) went to prod as prod-side patches; staging's copies differ (see category 5).
  • Direct-to-master, untraceable: commits like “Apply suggestions from code review”, “Potential fix for pull request finding” and “use trae.ai to fix the issue, can build” were committed straight onto prod history with no ticket ref.
  • The gateway's own history says it best: “restore Ocelot routes + Program.cs (lost in main→uat merge)” — a previous promotion destroyed prod code and had to be hand-restored.

Why this keeps happening — root causes & fixes

1 · Environment branches are separate lineages, not a ladder

staging/uat/master last shared a common ancestor in January 2026 (API, AdminWeb; CustomerWeb February, gateway May). Promotions copy patches (cherry-pick / re-apply) instead of merging one lineage upward, so git can no longer prove “what's in prod is what we tested”. Every category above is a symptom of this one fact.

Fix: adopt the ADR-0017 model fully — one feature branch per ticket family, replayed up staging → uat2 → master (git rebase --onto), merged with merge commits, never squashed; and schedule a one-time reconciliation that makes master an ancestor-consistent target again (back-merge or re-baseline).

2 · Hotfixes land on prod and never come back

193 commits of prod-only content (category 4) — hotfixes, platform upgrades, config — were applied to master directly and never back-ported. Staging tests the wrong platform, and the next promotion can revert prod fixes (it already did once, in the gateway).

Fix: a standing rule — any commit that lands on master must be back-merged (or consciously recorded as prod-only) the same day, and run release-check's reverse-diff before every train.

3 · Ticket status is decoupled from git reality

24 tickets say “in production” with no code in prod (category 3); cancelled tickets keep their commits on release branches (category 2). Status is flipped by automation on PR events, not on deploy, so the tracker answers a different question than “is it live?”.

Fix: the proof of “in production” is git merge-base --is-ancestor <sha> origin/master — wire the cockpit's git-first reconciliation (Inbox #74 flow) to flag every mismatch, and make “cancelled” trigger a mandatory revert-or-unblock decision while the code is still unmerged.

4 · The four repos don't promote together

A feature spans API + gateway + two SPAs, but each repo has its own train on its own schedule — the gateway hasn't had a prod release since 28 June while its API keeps shipping. Result: category 1 (split features) and gateway 404s. New API endpoints also silently 404 without a matching Ocelot route.

Fix: promote per feature, not per repo — a train manifest lists every repo's PRs for the feature and they gate on each other (bin/check-api-gateway-routes.sh as a release gate for the gateway leg).

5 · Trains are too big and too rare

~200 tickets and 21 migrations are queued; median pending age ~2 months. Big rare trains make every prod release a high-risk event and make “what broke?” impossible to bisect.

Fix: smaller, more frequent trains (weekly), and burn down the “verified / to deploy” group (40 tickets) first — it's finished work that only needs a ride.
